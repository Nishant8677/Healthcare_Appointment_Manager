# Deployment

Everything is described by [`render.yaml`](../render.yaml) at the repository root: a
PostgreSQL database, the API (which also runs the three background workers), and the portals
as a static site. One provider, one dashboard, one deploy log.

Free tiers throughout, which is fine for a demo and has two consequences worth knowing before
you conclude something is broken:

- **The API sleeps after 15 minutes of inactivity.** The first request after that takes
  roughly 30–60 seconds while the container starts. Subsequent requests are normal. If you
  are sending someone a link, open it yourself a minute beforehand.
- **A free Render database is deleted after 30 days.** For a submission that is usually
  longer than it needs to live, but note the date.

---

## 1. Push the repository

Render deploys from GitHub, so the repository has to be there first, on `main` and public.

```bash
gh repo create Healthcare_Appointment_Manager --public --source=. --remote=origin --push
```

## 2. Create the blueprint

In the [Render dashboard](https://dashboard.render.com/): **New → Blueprint**, connect the
repository, and Render reads `render.yaml`.

It will ask for the two values marked `sync: false`. **Leave both blank for now** — neither
URL exists yet. Click through and let it build.

This creates three things: `ham-postgres`, `ham-api` and `ham-web`. The first build takes a
few minutes.

## 3. Wire the two services together

The API needs the portals' URL to allow their requests; the portals need the API's URL to
send them. Neither exists until step 2 finishes, which is why this is separate.

Copy both URLs from the dashboard — they look like `https://ham-api.onrender.com` and
`https://ham-web.onrender.com`.

**On `ham-api`** → Environment:

| Variable | Value |
| --- | --- |
| `CORS_ORIGINS` | the **ham-web** URL, no trailing slash |

**On `ham-web`** → Environment:

| Variable | Value |
| --- | --- |
| `VITE_API_BASE_URL` | the **ham-api** URL, no trailing slash |

Then redeploy **ham-web**. `VITE_API_BASE_URL` is read at *build* time and baked into the
bundle, so a restart is not enough — it needs a rebuild. `CORS_ORIGINS` is read at startup, so
saving it restarts `ham-api` on its own.

> If the portals load but every request fails, this step is almost always why. The browser
> console will say the response was blocked by CORS, or the network tab will show requests
> going to `localhost:8000`.

## 4. Create the demo data

The seed builds a clinic that already looks lived-in: three doctors with different
specialisations and hours, three patients, and appointments in every state — one upcoming with
a symptom form, one completed with a prescription and its medication reminders, and one the
clinic cancelled because a doctor took leave. All of it is created through the real services,
so what you are looking at is the system's own output.

On `ham-api` → **Shell**:

```bash
DEMO_PASSWORD='choose-a-password' uv run python -m app.cli seed-demo
```

It prints the accounts it created. **Record the password** — it is stored nowhere else, and
there is deliberately none in the repository.

| Role | Email |
| --- | --- |
| Admin | `admin@clinic.demo` |
| Doctor | `asha.rao@clinic.demo` · Cardiology |
| Doctor | `nikhil.bose@clinic.demo` · Dermatology |
| Doctor | `fatima.khan@clinic.demo` · General Medicine |
| Patient | `meera.iyer@example.com` |
| Patient | `daniel.osei@example.com` |
| Patient | `priya.nair@example.com` |

The seed refuses to run against a database that already contains accounts it did not create.
An empty database is by definition not a running clinic; one with accounts in it might be, and
adding shared-password logins to a real medical system is not something to do by accident.
Running it twice is harmless — it reports that it is already seeded and changes nothing.

If you would rather start from an empty clinic, create only an administrator:

```bash
ADMIN_PASSWORD='choose-a-password' uv run python -m app.cli create-admin \
  --email you@example.com --name "Your Name"
```

## 5. Check it

```bash
curl https://ham-api.onrender.com/healthz
curl https://ham-api.onrender.com/readyz
```

`/healthz` never touches the database, so it answers even when Postgres is down; `/readyz`
reports `503` if the database is unreachable, which is what Render's health check watches.

Then open the portals and sign in as each of the three roles. The interactive API
documentation is at `https://ham-api.onrender.com/docs`.

## Optional: the real integrations

The deployment works without either of these. Both are off by default so a demo cannot run up
a bill or send mail to a real address.

### A real model, for real summaries

Without this the summaries are generated by a stub whose every field is prefixed `[stub]` —
deliberately unmistakable, because plausible-looking synthetic clinical text reaching a screen
would be worse than obviously fake text.

Two providers are supported. **Gemini has a free tier**, which makes it the easier one to
demonstrate with.

On `ham-api` → Environment:

| Variable | Value |
| --- | --- |
| `LLM_PROVIDER` | `gemini` or `anthropic` |
| `LLM_API_KEY` | from [aistudio.google.com](https://aistudio.google.com/apikey) or [console.anthropic.com](https://console.anthropic.com/) |

Leave `LLM_MODEL` unset — each provider resolves to its own default (`gemini-3.7-flash` or
`claude-opus-5`). Setting it to a model the other provider owns is the one configuration
mistake this cannot catch for you.

Then confirm it from the Render shell, rather than by booking an appointment to find out:

```bash
uv run python -m app.cli check-llm
```

That sends one real request through the whole path — settings, client selection, the request
shape, the response walk, schema validation — and prints the urgency and questions it got
back. A key that works in `curl` but not in this code is exactly the failure worth catching
before a patient's booking depends on it.

The API refuses to start if a real provider is selected and the key is missing, rather than
falling back to the stub and serving canned text as though it were a clinical summary.

Cost is small: two calls per appointment, a few hundred output tokens each. Note that Gemini's
flash model reasons by default, so its token usage is higher than the visible answer suggests.

### SendGrid, for real email

Without this, every message is written to the log instead of being sent — visible in Render's
log stream, which is enough to demonstrate the outbox working.

| Variable | Value |
| --- | --- |
| `EMAIL_PROVIDER` | `sendgrid` |
| `EMAIL_API_KEY` | your SendGrid key |
| `EMAIL_FROM` | a verified sender address |

**The seeded patients use `@example.com` addresses**, which is a reserved domain that accepts
nothing. Real delivery therefore needs real accounts — register one through the portal with an
address you own.

### Google Calendar

See [google-calendar-setup.md](google-calendar-setup.md). The redirect URI must be the
deployed API's callback:

```
https://ham-api.onrender.com/calendar/callback
```

Unset, the feature is inert rather than broken: nobody can connect a calendar, no sync row is
ever written, and every other part of the system behaves normally.

## Deploying somewhere else

Nothing here is Render-specific beyond `render.yaml`. The two services are:

**API** — any Python 3.11+ host that can run one process and reach Postgres.

```bash
pip install uv && uv sync --frozen          # build
uv run alembic upgrade head && uv run python run.py   # start
```

`run.py` binds `0.0.0.0` and reads `$PORT` when `APP_ENV=prod`, and `127.0.0.1:8000`
otherwise. The workers run inside the same process; set `BACKGROUND_WORKERS_ENABLED=false` on
web instances and run one dedicated instance with it `true` if you scale out.

**Portals** — any static host.

```bash
npm ci && VITE_API_BASE_URL=https://your-api npm run build   # serve ./dist
```

The host must rewrite unknown paths to `index.html`, or reloading any page but `/` returns a
404.

Every variable either service reads is listed in [`.env.example`](../.env.example) and in the
configuration table in the [README](../README.md).
